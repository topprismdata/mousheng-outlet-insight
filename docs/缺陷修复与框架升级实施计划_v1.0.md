## 0. 背景与修复原则

### 0.1 五大缺陷（战略评估结论）

| # | 缺陷 | 严重度 | 根因 |
|---|---|---|---|
| D1 | 自然语言解析器脆弱（正则/关键词，长尾问法覆盖率无测量，英文直接降级全表） | 🔴 最高 | 纯规则解析无 LLM 意图层，未采用行业混合意图架构 |
| D2 | 评估体系自我指涉（52 组基准由开发者自建自验，PRD 的"专家认可率 80% / 首次解释正确率 90%"均未测量） | 🔴 高 | 无真人盲测、无金标集、无 judge 校准 |
| D3 | 洞察深度为模板级（仅 descriptive + 统计标记，无显著性检验、无归因、无稳健性论证） | 🟡 中 | `_synthesize_*` 为固定话术，未接统计/因果工具 |
| D4 | 空间能力缺失（无经纬度，伪空间场景混入基准库，无法做商圈辐射/自蚕食/渗透率） | 🟡 中 | 数据缺经纬度；无空间索引与计算栈 |
| D5 | 本体生产未工具化（新数据集接入成本未度量，语义映射全手工） | 🟡 中 | 无剖析→草拟→认证流水线 |

### 0.2 修复原则（本次评审确认）

1. **能整体采用别人成熟框架的，替换自研模块；不自研框架级代码。**
2. **自研只保留三样核心 IP**：领域本体（field_registry + profile.lock）、洞察契约（双 Schema + insight.py）、确定性防火墙（validate_query 瘦身版）。
3. **全部选型许可证限于 MIT / Apache-2.0**（ISV 商用零传染风险）；全部选型要求数据本地驻留（不出域）。
4. **每个阶段有独立回滚方案**；52 组基准回归测试为全程安全网。

## 1. 框架选型结论（已定，详见《框架对比分析》）

| 方向 | 选型 | 许可证 | 对自研代码的影响 |
|---|---|---|---|
| ① NL2SQL 引擎 | **Vanna AI**（主）+ 现有 DSL（C 类规则排行兜底） | MIT | **替换** nl_parser.py + engine.py 执行部分 |
| ② 评估体系 | **Arize Phoenix** 开源版（主）+ promptfoo（CI 断言） | MIT | 新增能力（原空白） |
| ③ 数据质量 | **Evidently AI** + 保留 DenialConstraint 业务规则层 | Apache-2.0 | **替换** data_assertions.py 统计部分 |
| ④ 因果诊断 | **DoWhy**（仅 DAG + 反驳检验，先 2 周 PoC） | MIT | **增强** insight.py anomalies 块 |
| ⑤ 空间栈 | **H3 + DuckDB Spatial** + deck.gl H3HexagonLayer 渐进替换 | Apache-2.0 | 新增能力（原空白） |
| ⑥ 本体生产 | 当下轻量向导（ydata-profiling + LLM 草拟 + 人工认证）；**DataHub 预留**（数据集 >5 个时引入） | Apache-2.0 | 新增 onboard 向导（唯一允许的自研例外，产出物即核心 IP） |

**栈收敛红利**：Vanna 与 DuckDB 官方互认 → 方向①⑤共享 DuckDB 单引擎；六选型无一要求数据出域。

## 2. 分阶段实施计划

### P0 查询层换血（第 1–2 周）🔴 最高优先级

**目标**：用 Vanna 替换自研解析/执行主链路，解析覆盖率从估计 <60% 提升至 ≥90%，52 组基准零回归。

**前置依赖**：无（可立即启动）。

| 任务 | 内容 | 产出 | 验收标准 |
|---|---|---|---|
| T0.1 | 引入 DuckDB，直读现有 parquet；建立 `duckdb_adapter.py`（~100 行） | 数据层切换完成 | 62.9 万行加载 <3s；现有 A/B 类查询结果与 pandas 逐行等价 |
| T0.2 | Vanna 接入：`query_memory.jsonl` 52 组黄金查询灌入训练集；`field_registry` 字段说明注入文档上下文；LLM 后端默认接入（OpenAI/DeepSeek 任一，可配置） | Vanna 训练完成 | 52 组基准问题 Vanna 生成 SQL 执行结果与现有引擎一致率 ≥95% |
| T0.3 | 防火墙改造：`validate_query` 瘦身为 SQL 静态检查器（只读语句、字段白名单来自 field_registry、行数上限 10 万、超时 5s） | `firewall.py` | 注入测试：DROP/UPDATE/越权字段/全表扫 100% 拦截 |
| T0.4 | 双轨路由：A/B 类走 Vanna；C 类规则排行走现有 DSL 通道（保留 parse_C + RuleQuery） | 路由层 | C 类 8 组基准（Q37–Q44）结果与现引擎逐行等价 |
| T0.5 | 退役清理：nl_parser.py、engine.py、agent_core.py 执行部分归档至 `legacy/`；run_tests.py 改造为双轨回归 | 退役报告 | 全量测试套件（4 专项 + 52 基准 + 13 端到端）全绿 |
| T0.6 | 长尾盲测集建设：征集 50 条非开发者编写的口语问法（含错别字/英文/省略句） | 盲测集 v1 | Vanna 通道解析成功率 ≥90%（人工判定意图正确） |

**回滚方案**：legacy/ 目录完整保留旧链路，`QUERY_ENGINE=vanna|legacy` 环境变量一键切换。

**风险**：Vanna 对中文口语生成 SQL 准确率不达预期 → 缓解：T0.6 提前于 T0.5 执行，若 <75% 则触发方案 B（WrenAI 进程隔离部署评估）。

### P1 评估体系（第 3 周，与 P0 尾部并行）

**目标**：建立真人盲测金标集与 judge 校准流水线，产出 PRD 两个验收指标的真实数字。

**前置依赖**：T0.6 盲测集就绪。

| 任务 | 内容 | 产出 | 验收标准 |
|---|---|---|---|
| T1.1 | Phoenix 开源版自托管部署；接入查询链路 trace（问题→SQL→结果→InsightPackage 全链路） | trace 采集就绪 | 每次查询自动生成完整 trace |
| T1.2 | 盲测执行：3–5 名业务专家对 50 条盲测题结果打标（1–5 分 + 是否回答了问题 + 是否越界） | 金标集 v1 | 每题 ≥3 人打标，标注一致率（Cohen's κ）≥0.6 |
| T1.3 | judge 校准：用金标集校准 LLM-as-judge prompt，测量人机一致率 | 校准报告 | judge 与专家一致率 ≥80%（行业达标线） |
| T1.4 | promptfoo CI 断言集：越界词扫描（派单/拜访/排程…）、拒答场景断言、11 字段 Schema 校验 | CI 配置 | 每次 PR 自动运行，BCT-01~06 等价断言迁移完成 |
| T1.5 | 失败案例回流：低分案例自动写入 memory.py :fix 纠偏闭环 | 纠偏闭环打通 | 首轮失败案例 100% 进入待审队列 |

**验收里程碑（M1）**：产出《盲测评估报告 v1》，含**首次解释正确率**与**专家认可率**两个真实数字，对照 PRD 目标（90% / 80%）给出差距分析。

**风险**：找不到 3–5 名业务专家 → 缓解：老板协调客户方业务人员；最低 2 人也可启动，标注一致率阈值放宽说明。

### P2 质量与诊断（第 4–5 周）

**目标**：数据质量报告可视化嵌入产品；洞察块升级含显著性检验与稳健性论证。

| 任务 | 内容 | 产出 | 验收标准 |
|---|---|---|---|
| T2.1 | Evidently 替换 data_assertions 统计层：列分布漂移（KS/JS）+ 缺失率 + 新值检测；保留 DenialConstraint 业务规则层叠加 | `quality_report.py` | 现有 T37 漂移测试场景等价迁移；HTML 报告嵌入 demo Quality 卡片 |
| T2.2 | 显著性检验层：differences.metric_contrasts 附 Mann-Whitney U p 值 + Cohen's d 效应量；p>0.05 强制置信度措辞降级 | insight.py 诊断层 v1 | CQ-004 升级版通过；新增"差异不显著"降级用例 |
| T2.3 | DoWhy PoC（2 周封顶）：仅用 DAG 建模 + placebo/refuter 反驳检验，对"高分低流异常"结论做稳健性论证；产出写入 anomalies.baseline_method 与 limitations | PoC 报告 | 至少 2 个黄金场景的反驳检验跑通；若增益不明确则止损关闭该方向 |
| T2.4 | 新增黄金场景 CQ-011（指标冲突诊断：高分低流/低分高流归因） | 测试用例 | 纳入 test_insight_quality.py，全绿 |

**风险**：观察性数据上 DoWhy 反驳检验增益不明确 → 已设 2 周止损线，PoC 失败不阻塞主线。

### P3 空间层（第 6–8 周）

**目标**：补齐真实空间计算能力，地图从行政区聚合升级为 H3 六边形热力。

**前置依赖（关键路径，非框架）**：经纬度数据获取。

| 任务 | 内容 | 产出 | 验收标准 |
|---|---|---|---|
| T3.1 | 高德地理编码批量解析 62.9 万条地址（分省分批 + 配额管理 + 失败重试 + 约 10% 失败率兜底策略） | 带经纬度 parquet | 解析成功率 ≥85%；失败记录单独归档供人工补录 |
| T3.2 | DuckDB Spatial + H3 扩展开启；res-9 六边形索引入 DM 层 | 空间索引就绪 | 全量索引构建 <5min |
| T3.3 | 空间算子：商圈辐射（k-ring 客流加总）、自蚕食预警（同品牌 500m 密度 vs 单店客流）、网格渗透率 | `spatial.py` | 新增黄金场景 CQ-012（H3 商圈渗透率）通过 |
| T3.4 | 可视化：deck.gl H3HexagonLayer 渐进替换 demo 地图（保留行政区模式切换） | demo 地图 v2 | 双模式切换流畅；六边形热力正确渲染 |
| T3.5 | 伪空间场景治理（**立即执行，不等待 P3**）：Q15/Q16/Q18 等场景 desc 改注"关键词过滤"，limitations 显式声明 | 基准库修订 | 0 伪空间声明残留 |

**风险**：地理编码成本与配额（约几百元 + 高德企业配额）→ 需老板审批预算；失败率超 20% 则空间层降级为"试点区县先行"。
