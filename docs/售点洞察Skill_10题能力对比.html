售点洞察 Skill · 10 题能力对比

全部题目均在真实数据（629,074 行 × 153 列）上实跑，左列为本 Skill 实测输出，右列为"把 Schema 直接丢给大模型"的典型失效点 · 2026-07-24
核心区别一句话：本 Skill 把客户业务黑话 + 数据真实形状沉淀成确定性语义层，让任何解析器（含大模型）都只能在护栏内跑——查得准（实体/度量对齐）、错不了（编译期拦截幻觉）、还能给决策建议（派单体检），规模上有逃生舱（DataFusion / DataSketches）。以下 10 题逐条印证。
本次顺带修复做这份对比时实测发现一个真 bug：route_metric 从未接收进程内画像、且业态参数写死为 None，导致"住宿按评分排序"错误路由到餐饮的点评评分列。已修复（画像回退 + 从渠道组推断业态），并通过 34/34 全量回归。第 2、3 题即此能力的实证。
1
私有实体 + 区域 + 潜力字段消歧（A 类复合）
考察：把内部黑话"美宜佳""潜力"对齐到确定的物理列，并链式过滤 + 排序
问浦西大区未服务的美宜佳，按月均收入潜力预测从高到低取前 10
✓ 本 Skill 实测
  • "美宜佳" → 连锁品牌名称 contains 美宜佳（实体字典确定性展开）
  • "潜力" → 月均收入潜力预测(无协议无冰柜)（3 个潜力列里选对口径）
  • 链式：浦西 138,745 → 美宜佳 346 → 命中 37 行，输出 TOP10
filters: 规划大区=浦西大区, 服务状态=未服务, 连锁品牌名称 contains 美宜佳 order_by: 月均收入潜力预测(无协议无冰柜) desc
✗ 直接问大模型
  • "美宜佳"在 Schema 里没有——不知它是 连锁品牌名称 的一个值，容易漏查或去猜别的列
  • "潜力"对应 3 个几乎同名的列（如有协议/如有冰柜/无协议无冰柜），大模型无从判断口径，选错则结果全变
  • 无法保证过滤链顺序与 155 个列名逐字正确

模糊度量"评分"按业态路由 · 住宿本次修复
考察：同一个"评分"，在住宿业态下必须指向携程综合评分
问住宿客户按评分从高到低排序取前 10
✓ 本 Skill 实测
  • "评分" 按业态覆盖率路由 → 携程-综合评分
  • 体检自动切到住宿维度：审计房间数 / 携程星级，不误报点评
order_by: [携程-综合评分 desc]
✗ 直接问大模型
  • 数据里并存"携程-综合评分""大众点评餐饮点评评分星级"等多个评分列
  • 大模型极易把住宿的"评分"错套成餐饮点评列（正是本次修复前的表现）

业务度量口径确定性展开（measure）
考察：模糊阈值词"高评分"应展开为受管口径，而非模型猜阈值
问餐饮高评分的客户清单取前 10
✓ 本 Skill 实测
  • "餐饮高评分" 命中语义层度量 → 大众点评餐饮点评评分星级 >= 3.8
  • 命中 131,457 行；阈值由业务定义写死，人人一致
filters: [大众点评餐饮点评评分星级 >= 3.8]
✗ 直接问大模型
  • "高评分"到底是 ≥4.0 还是 ≥4.5？大模型每次可能给不同阈值，结果不可复现
  • 业务口径无处沉淀，换个人问就是另一套标准
5
自定义多规则排行 + 派单体检（C 类）
考察：把一段复杂业务规则编译成"基数 + 排序 + 达标占比"的可执行打分，并给决策建议
问商场里餐饮客户不低于 20 家为达标，周末客流从高到低排序，点评评分 3.8 分以上占比 50% 以上为高，开业 3 年以上占比 50% 以上为高
✓ 本 Skill 实测
  • 自动识别为 C 类，候选维度 经营场所名称，编译出 3 条规则：
  • ① 餐饮基数 ≥20（count）② 评分3.8占比≥50%（ratio）③ 开业3年占比≥50%（ratio）
  • 输出候选打分 + 高/中/低等级 + 「数据完整度%」列
  • 体检结论："全部候选数据完整度达标，可优先派单"
经营场所名称,餐饮基数,评分高占比,开业年限达标占比,达标率,等级,完整度% 润通欧尚中心城, 27, 0.52, 0.52, 1.0, 高, 98.3 港城新天地一期, 21, 0.76, 0.57, 1.0, 高, 95.4
✗ 直接问大模型
  • 这类"分组算达标占比再打分"逻辑，大模型直接生成代码极易在分母/空值/口径上出错，且无从校验
  • 更没有"能不能派单"的数据完整度体检——查完不知道结果可不可信

分布探索 + 幻觉短语防护（B 类）
考察："各个大区"是分组意图，不能被误当成某个大区的过滤值
问各个大区的餐饮客户分布
✓ 本 Skill 实测
  • 正确识别为 B 类：渠道组=餐饮 + group_by 规划大区
  • 输出 7 个大区的客户数分布（曾修复过"各个大区"被贪婪正则误当过滤值的 bug）
group_by: [规划大区] metrics: count → 7 个分组
✗ 直接问大模型
  • 易把"各个大区"当字面值去 规划大区 = '各个大区'，返回 0 行还看不出错
  • 意图（分组 vs 过滤）判断不稳定，措辞稍变就翻车
7
编译期护栏：拦截幻觉字段与非法算子（负向）
考察：宁可在编译期明确报错，也绝不在运行期静默产出错误数据
问（模拟解析器/大模型吐出的非法 DSL）按"老板年龄">40 筛选 · 对类别字段"渠道组"用 > 算子
✓ 本 Skill 实测
  • 幻觉字段：老板年龄 不在语义层 → 编译期拒绝
  • 类型不兼容：类别字段 渠道组 不支持 > → 拒绝并列出允许算子
  • 合法查询照常通过（对照组 ok=True）
✗ 字段「老板年龄」不在语义层（疑似幻觉，编译期拒绝） ✗ 字段「渠道组」(category) 不支持算子 >
✗ 直接问大模型
  • 生成不存在的列名照样能跑出"看似合理"的结果，错误静默发生、难以察觉
  • 类别字段用数值比较通常返回空集，被误读为"没有符合条件的客户"

多步会话 · 工作集在追问间收缩
考察：连续追问时状态化传递结果集，而不是每次从全量重查
问① 美宜佳清单 → ② 这些里浦西大区的 → ③ 看它们的经营场所分布
✓ 本 Skill 实测
  • ① 美宜佳 → 工作集 346 行
  • ② "这些里" 自动 scope=current，在 346 上再筛 → 37 行
  • ③ "它们的" 在 37 行上聚合 → 20 个经营场所分组（工作集不变）
346 →(这些里浦西)→ 37 →(它们的分布)→ 20 组
✗ 直接问大模型
  • 无持久工作集，"这些/它们"指代靠拼历史文本，长对话极易丢失或指错上下文
  • 每轮都得把前一步条件重述，否则回到全量算错
9
可选 DataFusion 计算后端 · 与 pandas 逐值等价
考察：同一语义查询可切换到向量化 SQL 引擎，结果不变——为超内存/高并发留逃生舱
问各个大区的餐饮客户分布（分别用 --engine pandas 与 --engine datafusion）
✓ 本 Skill 实测
  • pandas → 7 组；DataFusion → 7 组，结果一致
  • DataFusion 自动把 DSL 编译成 SQL（下方），护栏两条路径共用
  • 翻译不了的算子/C 类自动回退 pandas，默认仍是 pandas 零回归
SELECT "规划大区", COUNT(*) AS "客户数" FROM sh WHERE "渠道组" = '餐饮' GROUP BY "规划大区" ORDER BY "客户数" DESC
✗ 直接问大模型
  • 换引擎意味着换一套代码，难保证与原逻辑逐值一致
  • 数据超内存时直接 pandas 全量 load 会 OOM，没有平滑的规模退路
10
DataSketches 近似画像 · 单遍流式估分位数
考察：超大数据首扫时用流式 sketch 近似统计，精度足够、成本大降
问字段"周末均值客流(人)"的画像：精确 vs --approx
✓ 本 Skill 实测
  • 中位数：精确 4740 vs 近似 4755（误差 0.3%）
  • 中心分位 p25：2128 vs 2141 · p75：10272 vs 10290（<1%，KLL 设计对中心准）
  • 低尾 p1：精确 159 vs 近似 198（误差约 24%，KLL 对极端尾部误差偏大，属预期）
  • 近似模式不读写精确缓存，两者严格隔离；sketch 数值因内部随机略有浮动（每次 ±<1%）
精确 median=4740 p1=159 p25=2128 p75=10272 近似 median=4755 p1=198 p25=2141 p75=10290 (KLL)
✗ 直接问大模型
  • 大模型不做实际计算，"分位数"只能靠生成代码全量算，超大数据慢且耗内存
  • 没有"用可控误差换速度"的流式近似能力
