## 1. 背景与问题陈述

### 1.1 业务背景
售点 / 门店 / 潜客数据通常是**宽表 + 业务黑话**：本项目真实输入为 152/<n_cols> 列（不同快照存在一列差异），混着省份/大区/业态/连锁品牌/携程住宿指标/大众点评评分/客流等，且大量"业务语义"并未在物理 Schema 里显式编码（例如"评分"在住宿指向携程综合评分、在餐饮指向大众点评评分；"潜力"有 3 个互不相同的预测列）。

### 1.2 核心痛点
直接把 Schema 丢给通用大模型会出现三类失效（均有真实数据实跑佐证）：
1. **私有实体对齐失败**：不知道"美宜佳"是 `连锁品牌名称` 的取值，写成 `df['品牌']` → `KeyError`（真实执行验证）。
2. **度量口径幻觉**：同一"评分"词，跨业态指向不同列；阈值靠模型拍脑袋（4.0 / 4.5 / 3.8 每次不同），结果不可复现。
3. **静默错数据**：大模型可生成语义层之外的字段或非法算子，pandas/SQL 照跑，返回看似合理实则其错的数字，且发现不了。

### 1.3 论文依据（已联网核实）
本项目定位为论文《基座模型平权时代独立数据服务商的壁垒重构》所主张架构的**可运行实证**：平权后 ISV 的壁垒不在"写 SQL"，而在"把客户未编码的业务语义翻译成结构化、确定性的机器逻辑"。

## 2. 目标与非目标

### 2.1 目标（Goals）
- G1：把"中文自然语言 → 售点数据查询"做成**确定性、可复用**的能力，任何解析器（包括未来可插拔的模型解析器）只能在语义层护栏内产出 DSL。
- G2：覆盖 A 明确条件查询 / B 分布探索 / C 自定义规则排行三类需求，且查询后**主动做决策体检**给出派单建议。
- G3：具备进阶能力（会话多步、Dry-plan、RAG 自学飞轮、MCP 暴露、统计画像、双引擎、端到端洞察、时间谓词），形成"分析飞轮"。
- G4：以**零 LLM 依赖**为当前交付底线（默认纯 pandas 执行），保住无网/无密钥也能跑；仅预留可插拔解析器接口，当前版本不调用第三方大模型 API。
- G5：支持业务标签**按需定义、即时计算**；新增业务标签原则上不扩充物理宽表、不等待全量 ETL，高频且稳定的标签再选择性物化。
- G6：作为客户现有数仓/湖仓之上的**语义与决策控制面**运行，兼容轻量文件模式与企业 Warehouse Adapter 模式，不要求客户重建数仓。
- G7：面对无法可靠理解的业务语义时能够识别不确定性、主动澄清、记录用户纠正，并通过离线学习持续优化澄清策略。
- G8：与现有 BI 双向集成：共享指标、权限、筛选上下文与证据；重点替代长尾取数、临时筛选、动态标签和连续决策工作。

### 2.2 非目标（Non-Goals）
- NG1：不做通用 Text-to-SQL 生成器（不面向任意数据库，专注售点领域语义层）。
- NG2：不以重建完整企业 BI 平台为目标；当前不替代固定经营驾驶舱、正式报表、订阅分发和复杂可视化设计，但重点替代传统 BI 中依赖预制数据集的长尾取数、临时筛选、动态标签与连续分析。
- NG3：当前版本不集成第三方大模型 API；未来若增加可选自然语言润色或 LLM-judge，必须位于确定性结果之后，且不得改写 DSL、指标口径或结构化结果。
- NG4：不做实时数据流处理（面向静态 parquet/CSV 快照）。
- NG5：不允许强化学习或单次用户反馈在线修改生产指标口径、动态标签定义、权限规则或物理绑定；所有学习结果必须经过离线评估、审核、版本发布与回滚机制。

## 4. 核心概念与术语

- **语义层（Semantic Layer）**：`references/field_registry.json`，含字段别名、业务度量 `measures`、私有实体字典 `domain_entities`。
- **DSL**：统一结构化查询语言，三种类型：
  - `A` 明确条件：`{filters, order_by, limit}`
  - `B` 分布探索：`{group_by, metrics:[count]}`
  - `C` 规则排行：`{candidate, rules:[...]}`
- **确定性编译护栏**：`validate_query` 在编译期拒绝语义层外字段、算子/类型不兼容。
- **工作集（Working Set）**：会话态中逐轮收缩的当前结果 DataFrame。
- **时间谓词**：`close_after`/`open_after` 算子，解析「大众点评营业时间」自由文本。
- **原子事实（Atomic Facts）**：稳定沉淀的基础字段与事件，如区域、业态、品牌、评分、客流和营业时间；不预先穷举未来业务可能使用的全部标签。
- **动态标签（Dynamic Label）**：查询时依据业务规则、原子事实、适用业态和当前数据版本即时计算的临时业务属性，如“高潜餐饮”“夜间营业”“资料完整且值得派单”。动态标签可直接参与筛选、分群和排行。
- **选择性物化（Selective Materialization）**：对高频、稳定或计算昂贵的动态标签进行缓存或落表；默认仍以按需计算为主，避免重新形成标签大宽表。
- **语义与决策控制面（Semantic & Decision Control Plane）**：位于客户数据底座之上，统一管理实体、指标、关系、动态规则、权限、物理绑定、版本和血缘；它不是某一张 ADS 表。
- **Warehouse Adapter**：把统一逻辑关系计划编译/下推到 pandas、DataFusion、DuckDB、Snowflake、Databricks SQL、BigQuery、Trino 等具体执行环境的适配接口。
- **HIP（Human-in-the-loop Interactive Parsing）**：本项目对“人在回路交互式语义解析”的产品化简称；根据语义不确定性决定执行、澄清、展示候选或拒答，并从经验证的纠正日志中离线学习。它不是 HIPPO Gym 或 HIP-RL 的直接实现。
- **分析状态（Analytical State）**：当前会话和 BI 界面共享的指标、筛选器、时间范围、层级、选中对象、工作集和语义版本。

## 7. 技术与架构设计

### 7.1 目标数据流

> 当前已实现链路仍为“确定性解析 → DSL → validate_query → pandas/DataFusion → audit/insight”；以下为整合 HIP、逻辑计划、物化和 BI 上下文后的目标链路。
```
自然语言 / BI 当前状态
         → nl_parser.auto_parse → Top-K 语义候选
         → uncertainty（不确定性检测）
         → [明确] DSL(A/B/C) / [歧义] HIP 主动澄清 / [高风险] 拒答或转人工
         → semantic planner（实体/指标/关系/动态标签依赖图展开）
         → validate_query（字段/算子/类型/粒度/Join/权限确定性护栏）
         → materialization planner（虚拟计算 / 版本缓存 / 选择性物化）
         → Warehouse Adapter（pandas/DataFusion 默认；企业数仓规划）
         → audit + evidence + insight
         → DataFrame / CSV / JSON / 图表规范 / BI 筛选 / 洞察 / 行动建议
         → correction log（经验证反馈进入离线学习与审核队列）
```

### 7.3 设计原则
- **语义层中介 + 确定性编译护栏**（ISV 壁垒）：大模型无法直接引用物理表不存在的列。
- **原子事实稳定沉淀，业务标签按需生成**：数据底座不预判全部业务需求；语义层在查询时组合原子事实，形成动态标签、目标人群与优先级。
- **默认即时计算，必要时选择性物化**：新增标签原则上不改物理 Schema；仅对高频、稳定、昂贵规则做缓存或落表。
- **版本钉住后再谈复现**：结果复现必须同时固定自然语言、数据快照、语义注册表、产品/引擎版本及排序规则。
- **默认精确、可选近似/向量化**：pandas 默认，DataFusion/DataSketches 仅明确启用。
- **分析飞轮**：查询结果 → 洞察 → 建议下一步 → 连续追问；用户纠偏持久化。
- **安全学习而非在线改口径**：学习系统优化“何时澄清、澄清什么、如何排序候选”，企业事实与指标定义仍由受控语义层管理。
- **逻辑与物理解耦**：语义系统产出逻辑关系计划，Warehouse Adapter 决定具体 SQL/表达式、分区裁剪、缓存和物化能力。
- **与 BI 共享状态**：BI 提供当前筛选、指标、时间和选中对象；智能体在同一上下文继续分析并返回可固定为图表/数据集/人群的结构化结果。

### 7.4 与 Text-to-SQL / 通用大模型分析的架构差异

本产品不是“另一套自然语言生成 SQL”，也不让大模型直接绕过语义治理访问物理数据。三类方案解决的问题不同：

| 维度 | Text-to-SQL | 通用大模型直接分析 | 本产品：受控语义计算 |
|---|---|---|---|
| 核心目标 | 把问题翻译成 SQL | 根据 Schema / 数据临时生成代码与回答 | 把企业业务语义编译成可复用、可审计的决策逻辑 |
| 主要输入 | 表结构、字段描述 | Schema、样本数据、Prompt | 原子事实 + 私有实体 + 指标口径 + 适用条件 |
| 中间表示 | SQL | 模型内部推理 / 临时代码 | 统一 DSL + 动态标签规则 |
| “高潜门店”处理 | 依赖已有字段或临时 SQL | 模型临时猜测定义 | 依据已登记口径即时计算，口径可版本化 |
| 新标签产生 | 改 SQL、改表或重新加工 | 每次临时生成，难以复用 | 业务需求发生时按需组合；高频标签选择性物化 |
| 语义正确性 | SQL 可执行不等于业务口径正确 | 容易受模型、Prompt 和上下文影响 | 语义层确定口径，编译期校验字段、算子和类型 |
| 结果复现 | SQL 固定时可复现，但语义可能错 | 同问法可能产生不同代码或解释 | 同数据版本 + 语义版本 + 引擎版本下可复现 |
| 知识沉淀 | 分散在 SQL 与报表中 | 分散在对话与 Prompt 中 | 沉淀为实体、度量、标签规则、适用条件和纠偏记忆 |
| 模型关系 | 通常依赖模型生成 SQL | 模型是主要分析与回答主体 | 模型负责理解人话；语义系统负责保证答案，模型可替换 |

三类架构的数据流差异：

```text
Text-to-SQL：问题 → 大模型 → SQL → 数据库 → 结果
通用大模型：问题 + Schema + 数据 → 模型临时推理 → 代码 / 回答
本产品：问题 → 业务语义层 → 动态标签与规则组合 → 确定性校验 → 计算引擎 → 清单 / 排行 / 洞察 / 建议
```

**产品定位句**：Text-to-SQL 解决“如何生成查询”，通用大模型解决“如何生成回答”，本产品解决“如何把企业业务语义变成可信、可复用、可治理的决策逻辑”。

### 7.5 与 BI 的关系：部分替代、双向增强

本产品不重新建设完整 BI，但也不是附着在 BI 上的聊天插件。两者以统一语义层和分析状态协同：

| 工作类型 | 主责系统 | 关系 |
|---|---|---|
| 固定经营驾驶舱、正式报表、订阅分发、复杂视觉概览 | BI | 保留并增强 |
| 长尾取数、临时筛选、动态标签、连续追问、原因解释、行动名单 | 本产品 | 重点替代 |
| 指标定义、权限、筛选上下文、时间范围、证据与版本 | 共享语义控制面 | 共同可信底座 |
| CRM 派单、营销触达、业务写回 | 业务执行系统 | 本产品在审批后驱动 |

双向接口：

```text
BI → 智能体：dashboard_id / metric_id / filter_state / drill_path /
             selected_marks / time_range / semantic_version

智能体 → BI：dataset / chart_spec / filter_expression / dynamic_segment /
             evidence / suggested_followups
```

**产品表达**：BI 让企业持续看见已定义的问题；本产品让业务即时提出尚未定义的问题，并把答案沉淀为可执行、可复用的新决策规则。

若客户已有 BI 语义层，接入前必须确定指标唯一真源：

- 客户 BI 已认证指标优先时，本产品通过绑定引用，不复制另一套定义；
- 本产品动态标签可发布给 BI，但必须携带标签/数据/权限版本；
- 两边定义冲突时禁止自动合并或任选其一，进入语义负责人审核队列；
- BI 权限是访问策略来源之一，本产品在查询编译阶段执行等价或更严格的权限，不得降级；
- 写回 CRM/派单等重要动作必须经过客户定义的审批或授权策略。

## 10. 已知限制与偏差（诚实披露）

1. **"火锅"口径**：数据无纯火锅子渠道，`细分渠道` 为 `中档餐馆-火锅烧烤小龙虾川湘菜` 打包值。品牌名含"火锅"仅 4.5%（92/2051）；当前解析器把"火锅店"判为品牌名包含（269 家），非打包子渠道（2051 家）。在补齐消歧机制前，结果必须显式回显“品牌名包含”口径，不得静默呈现为全部火锅业态。
2. **时间谓词严格 >22:00**：闭店正好 22:00 整（555 家）不计入"晚10点以后"；营业时间取自大众点评。
3. **近似画像低尾误差**：KLL 对中心分位误差 ~0.3-0.8%，但低尾 p1 误差约 24%（预期行为）。
4. **DataFusion 当前无性能优势**：629k 行规模下 5.9ms vs pandas 4.3ms，定位为逃生舱（超内存/高并发）而非替代品。
5. **裸大模型对比边界**：当前沙箱无第三方大模型 API，对比报告中的"裸大模型输出"为基于真实 schema 的典型代码 + **100% 真实执行**结果，非某模型逐字 transcript。
6. **B 类指标范围**：当前分布探索只支持 `count`，尚不支持占比、去重计数、均值、中位数和分位数。
7. **会话可逆性**：当前工作集以逐轮收缩为主，虽可用 `scope=full` 回到全量，但尚无显式历史查看、撤销和回到指定轮次能力。
8. **未知语义处理**：当前解析器尚无校准后的不确定性评分和主动澄清策略；未登记语义主要依赖失败提示或人工补注册表。
9. **数仓接入边界**：当前仅对本地 Parquet/pandas/DataFusion 有实测证据；企业数仓、湖仓表格式、BI状态协议和权限下推均属规划能力。
10. **BI替代边界**：产品可替代长尾取数和动态决策工作，但未实现固定驾驶舱、正式报表、订阅分发和复杂可视化设计器。

## 12. 成功指标（衡量标准）

- M1：版本钉住的回归集 **36/36** 稳定产生相同 DSL 与结果快照。
- M2：已登记负样本中的语义层外字段、非法算子和类型不兼容全部在执行前被拒绝，并持续扩充负样本覆盖。
- M3：用户纠偏后，近义问法达到复用阈值（余弦 ≥0.82）；当前样本实测 0.83，后续报告样本量与分层命中率。
- M4：高频 A/B 查询 P95 <1 秒；复杂 C 类、多步与洞察分别记录 P50/P95，不把首扫画像计入查询延迟。
- M5：新增一个基于既有原子事实的动态标签，不改物理 Schema、不重跑全量 ETL，并在 1 个工作日内完成定义、验证和上线。
- M6：端到端语义正确率、Top-N 结果一致率及业务建议采纳率成为上线后的核心质量指标；裸大模型失败数量仅作为竞品研究证据，不作为本产品成功指标。
- M7：上线后单独统计**静默语义错误率**；高风险未知语义不得以“可执行”替代“语义正确”，目标值由真实标注集确定。
- M8：澄清有效率（一次澄清后得到已确认 DSL）、平均澄清次数、拒答准确率和澄清后执行正确率按场景分层报告。
- M9：纠正复用率、候选规则审核通过率、错误反馈污染率和规则回滚次数用于衡量 HIP 学习闭环质量。
- M10：动态标签记录虚拟/缓存/物化命中率、计算成本、刷新延迟和版本失效准确率；不得只报告平均查询时间。
- M11：同一指标在 BI、智能体、导出数据和业务系统中的版本一致率应为 100%；任何差异必须能够由版本或权限解释。

## 13. 数仓设计（Data Warehouse Design）

> 背景：本 Skill 当前直接消费一张 <n_rows> 行 × <n_cols> 列的贴源宽表（`<data>.parquet`）。本节不假设产品必须替客户重建数仓，而定义两种部署模式：轻量文件模式直接读取版本化 Parquet；企业模式通过 Warehouse Adapter 接入客户已有数仓/湖仓。产品核心是位于数据底座之上的**语义与决策控制面**，ADS 仅是可选物化结果，不等同于语义层。

### 13.1 现状诊断（真实数据实证）

基于 `profiler` 对真实 parquet 的列级画像：

| 反模式 | 实证数字 | 企业级影响 |
|---|---|---|
| 大量全空列 | **33 列（约 22%）100% 为空**（客资编号/名称/地址、KA名称、连锁名称、冰柜门数、TOP、NARTD/SOVI排面数、滚动12个月销售收入、据DC/办事处距离、乡镇属性、赶集日、建档时间、闪电仓*、重点客户名称/重点业态分类名称 等） | 存储与扫描浪费；Schema 噪声诱导幻觉 |
| 高缺失率列堆积 | **59 列（约 39%）缺失率 ≥90%**，其中 33 列全空 | 列裁剪无收益，但拖慢任何 `SELECT *` / 画像 |
| 多业务域混杂 | 单表混装 6+ 域：地理组织 / 渠道业态 / 连锁 / 携程住宿 / 大众点评 / 人口客流画像 / O2O / 乡镇 / KPI 死列 | 跨域 join 困难；稀疏域（携程缺失 0.93–0.99、点评 0.31–1.00）拉低整表密度 |
| 口径冗余 | `月均收入潜力预测` 三列（有协议 / 有冰柜无协议 / 无协议无冰柜）并存 | 语义歧义，裸模型无法区分 |
| 主键隐式 | `腾讯售点id` 为事实上业务主键（0 缺失），但物理层未约束；`经营场所` 多值逗号分隔 | 无法做外键化 / 维度退化 |
| 无分区 / 无聚簇 | 单一 parquet，无分区键、无 Z-Order | 任何大区/业态过滤都全表扫描 |

**结论**：当前物理表是**上游多源系统汇聚的 ODS 贴源快照**，并非为分析服务优化的数仓；其反模式是上游问题，不是 Skill 设计缺陷。Skill 的语义层与确定性护栏已将上述问题**隔离在语义层之下**——这正是企业数仓中「语义层 / 指标平台」应承担的职责。但作为可交付产品，应给出标准数仓建模方案，使本数据集可平滑接入企业数仓体系。

### 13.2 目标架构：数据分层 + 语义控制面

```
[渠道与行动]   BI驾驶舱 │ 售点洞察工作台 │ CRM/派单/API
                         ▲
[智能决策服务] 语义理解/HIP澄清 │ DSL护栏 │ 动态标签/排行/洞察
                         ▲
┌────────────────────────────────────────────────────────┐
│ 语义与决策控制面                                       │
│ 实体关系 │ 指标口径 │ 动态规则 │ 物理绑定 │ 权限/版本/血缘 │
└────────────────────────────────────────────────────────┘
                         ▲
[数据服务层]   Gold/DWS原子事实 │ 版本缓存 │ 可选ADS物化结果
                         ▲
[核心明细层]   Silver/DWD身份解析 │ 历史属性 │ 关系桥 │ DQ
                         ▲
[原始层]       Bronze/ODS原始快照 │ CDC/批次 │ 装载元数据
                         ▲
[企业数据源]   门店主档 │ CRM │ 点评/携程 │ 客流 │ 预测模型
```

- **Bronze/ODS**：原始数据按到达形态保存，附 `source_system / batch_id / loaded_at / schema_version / checksum`，供审计、回刷和重新建模。
- **Silver/DWD**：不是机械按来源拆表，而是完成身份统一、类型/编码标准化、历史属性、关系桥接、迟到数据处理与质量隔离。
- **Gold/DWS**：提供粒度明确、可复用的原子事实、一致性实体和度量；不预先穷举全部业务标签。
- **ADS/物化结果**：仅承载高频、稳定、昂贵或有明确新鲜度 SLA 的标签/数据集，可删除并由“事实 + 规则版本 + 数据快照”重建。
- **语义与决策控制面**：独立于物理分层，统一定义业务对象并生成逻辑计划；通过 Warehouse Adapter 绑定不同客户的物理表与引擎。

两种部署模式：

| 模式 | 数据底座 | 适用场景 | 产品责任 |
|---|---|---|---|
| 轻量文件模式 | CSV/Parquet + pandas/DataFusion/DuckDB | PoC、单机、629k 级快照 | 数据画像、版本快照、语义计算、结果证据 |
| 企业接入模式 | Snowflake/Databricks/BigQuery/Trino/Iceberg/Delta 等 | 企业已有数仓/湖仓 | Adapter、语义绑定、权限下推、逻辑计划、血缘与物化策略 |

责任边界（默认 RACI）：

| 事项 | 客户数据团队 | 本产品 | 共同决策 |
|---|---|---|---|
| 源系统接入、调度、存储、备份、平台运维 | A/R | C | 数据SLA |
| ODS/DWD/DWS 实施与上游数据修复 | A/R | C（提供参考模型与诊断） | 粒度/历史策略 |
| 售点身份解析算法、匹配候选和证据 | C | R | 客户对高风险匹配A |
| 业务指标、标签定义、适用条件 | A | R（建模、编译、版本） | 审核发布 |
| 权限策略来源 | A/R | R（编译与下推） | 冲突处理 |
| 查询执行、证据、缓存/物化建议 | C | A/R | 成本与新鲜度SLA |
| BI固定报表与可视化资产 | A/R | C/接口 | 共享语义和状态 |

> A=最终负责，R=执行负责，C=协作/咨询。具体项目可调整，但必须在上线前显式确认，尤其是身份匹配、指标唯一真源、权限和业务写回审批。

### 13.3 售点主题模型：身份、时间、关系与事实

#### 13.3.1 身份解析与来源映射

企业级模型不能假设腾讯售点、点评门店、携程酒店天然一一对应。增加：

| 对象 | 粒度与职责 |
|---|---|
| `entity_store` | 企业内部稳定 `store_id`，表示真实世界售点实体 |
| `store_source_identity` | `store_id × source_system × source_store_id × 有效期` |
| `store_platform_mapping` | 平台门店匹配方法、匹配分数、审核状态和有效期 |
| `store_merge_history` | 实体合并/拆分历史，保证历史结果可解释 |

平台匹配未经审核时，查询结果必须返回 `match_method / match_score / review_status`，不得把概率匹配静默当作事实。

#### 13.3.2 一致性实体与历史属性

**一致性维度（Conformed Dimensions）**

| 维度 | 业务键 | 关键属性 | SCD |
|---|---|---|---|
| `dim_store` | 企业内部 `store_id` | 当前名称、标准地址、经纬度、实体状态 | SCD1 当前视图 |
| `store_attribute_history` | `store_id × 属性版本` | 渠道、品牌、区域、分类等需要回溯的属性 | 按属性配置 SCD2 |
| `dim_geo` | 标准地理键 | 省/市/区、规划大区、OU、办事处、路线层级 | 组织变化需版本化 |
| `dim_channel` | 标准渠道键 | 渠道组、渠道、子渠道、细分渠道 | 分类体系需版本化 |
| `dim_venue` | 标准场所键 | 经营场所名称、场所类型 | SCD1 |
| `bridge_store_venue` | `store_id × venue_id × 有效期` | 解决经营场所多值和一店多场所关系 | 关系历史 |
| `dim_chain` | 连锁品牌ID | 连锁品牌名称、集团、来源 | SCD2（品牌归属会变更） |
| `dim_platform` | 平台代码 | 携程/大众点评等平台名称、来源系统、口径说明 | SCD1 |

#### 13.3.3 原子事实与严格粒度

**事实表（Fact Tables）**

| 事实表 | 粒度 | 关键度量 | 说明 |
|---|---|---|---|
| `fact_store_snapshot` | 售点 × 快照日 | 营业面积、NIQ-NARTD指数、服务状态 | 主事实，一行一售点；稀疏域不进主事实 |
| `fact_revenue_potential` | 售点 × 预测场景 × 模型版本 × 预测日 | 预测值、置信区间、特征快照 | 三套潜力不再固定为三列，支持场景/模型演进 |
| `fact_foot_traffic_snapshot` | 售点 × 快照日 | 平日/周末/日均客流、居住/办公人口、女性/青年占比、消费水平、房价 | 周期快照事实，不作为维度 |
| `fact_platform_store_snapshot` | 售点 × 平台 × 平台门店 × 快照日 | 评分、评论数、人均、营业状态、营业时间 | 保留来源门店粒度，避免错误聚合 |
| `fact_service_activity` | 售点 × 服务事件 | 接触、派单、拜访、转化等 | 为行动闭环和效果评估预留 |
| `fact_data_quality` | 售点 × 数据版本 × 质量规则 | 完整性、异常、匹配可信度 | 质量证据可直接参与动态标签 |

所有事实至少携带 `event/effective_time`、`snapshot_id`、`loaded_at`、`source_version`；需要历史一致性的查询使用 as-of Join。结果复现同时钉住数据快照、维度有效期、语义/标签版本和预测模型版本。

**逻辑 DDL 示例（伪 SQL，仅表达粒度与字段；不承诺跨 Spark/DataFusion/表格式直接执行）**

```sql
-- 一致性维度：地理组织
CREATE TABLE dim_geo (
  geo_sk     BIGINT,
  province   STRING, city STRING, district STRING,
  region     STRING,
  plan_ou    STRING, office STRING, supervisor STRING,
  route      STRING, koid STRING
);

-- 一致性维度：连锁（SCD2）
CREATE TABLE dim_chain (
  chain_sk         BIGINT,
  chain_brand_id   STRING, chain_brand_name STRING,
  chain_group_name STRING, chain_source STRING,
  valid_from DATE, valid_to DATE, is_current BOOLEAN
);

-- 售点主事实：一行 = 售点 × 快照日
CREATE TABLE fact_store_snapshot (
  store_sk    BIGINT,
  geo_sk      BIGINT,
  channel_sk  BIGINT,
  chain_sk    BIGINT,
  is_chain BOOLEAN,
  service_status STRING,
  biz_area    DOUBLE,
  niq_actual_area BOOLEAN,
  niq_nartd_idx    DOUBLE,
  snapshot_date DATE,
  snapshot_id STRING,
  loaded_at TIMESTAMP
);
```

> 主事实不同时重复保存 `geo_sk/channel_sk` 和未经声明的 `region/channel_group` 文本。确需保留事实发生时快照字段时，必须标注为退化维度并定义与当前维度不一致时的查询规则。

> 主键、外键、分区、聚簇、Z-Order 与布隆过滤由具体执行环境和表格式分别定义：Spark SQL、DataFusion、Delta/Iceberg/Hudi/裸 Parquet 的能力与语法不同，落地前必须选定组合并进行兼容性测试。

### 13.4 物理优化

| 手段 | 做法 | 收益（基于真实数据） |
|---|---|---|
| 列裁剪 | DWD 阶段 DROP 33 个 100% 空列；评估将 26 个(59−33) 90–99% 缺失列下推到可选域表（垂直分区） | 列数 152→~120，扫描/存储显著下降 |
| 列式存储 | Parquet + Zstd/Snappy 压缩；字典编码高频低基数列 | 列存天然压缩，仅读查询所需列 |
| 分区 | 优先按 `snapshot_date`；是否叠加 `region` 由数据分布、刷新频率和文件数基准测试决定 | 可裁剪无关快照/区域；不预先承诺固定跳过比例，避免小文件 |
| 聚簇 / Z-Order | 仅在所选表格式和执行引擎明确支持时，对高频过滤列评估聚簇或 Z-Order | 可能改善数据跳过；DataFusion 对具体布局的利用程度需实测 |
| 布隆/字典 | 低基数列用字典编码；布隆过滤仅用于高选择性等值条件 | 加速 `=` / `IN`；`contains '%词%'` 需规范化关键词列、倒排/三元组索引或专用搜索能力 |
| 稀疏域隔离 | 携程/点评进入独立平台周期快照事实，不进售点主事实 | 主事实密度提升，避免全表稀疏 |

### 13.5 ETL 管线与数据质量门禁

```
ODS ──▶ DWD ──▶ DWS
 │         │        │
 └─DQ门禁─┴────────┘
```

- **ODS→DWD**：列裁剪（去 33 空列）、类型矫正（日期/数值/布尔）、`腾讯售点id` 主键唯一性校验、编码统一（省/大区对照表）、垂直拆分稀疏域（携程/点评/人口）。
- **DWD→DWS**：维度外键化、连锁 SCD2、平台/客流周期快照事实、`CFD` 校验（Fan 2009：如「业态=住宿 ⇒ 应有携程评分」）；分区和聚簇策略在选定引擎/表格式后配置。
- **DQ 门禁**（贯穿）：① 空列检测（自动识别 100% 空列告警）；② 缺失率画像（复用 `profiler`）；③ PK 唯一性；④ 跨域一致性（路线→大区 映射）；⑤ 重复行检测。
- **调度**：静态快照全量刷新（对齐 NG4 不做实时流）；可选的增量/分区覆盖。

### 13.6 语义包 ↔ 数仓映射

`field_registry.json` 从单一字段注册表逐步演进为版本化语义包：

```text
semantic/
├── entities/            # 售点、品牌、平台门店、地理、渠道
├── dimensions/          # 维度、层级、时间语义
├── measures/            # 聚合方式、单位、可加性、适用条件
├── relationships/       # Join键、基数、有效期、桥接关系
├── dynamic_labels/      # 规则表达式、依赖图、证据模板
├── physical_bindings/   # 不同客户/引擎的表列绑定
├── policies/            # 行列权限、租户和敏感字段
└── versions/            # 审核、发布、灰度和回滚元数据
```

| 语义层对象（field_registry.json） | 数仓落点 |
|---|---|
| `fields.*`（省份/城市/规划大区/渠道组/细分渠道/连锁品牌名称/经营场所/携程-*/大众点评-*/客流…） | DWS 原子维度/事实列（物理改名不改语义层） |
| `measures.*`（餐饮高评分=点评评分≥3.8、客房100+、星级4+…） | DWS 一致性度量口径（唯一真源，杜绝口径幻觉） |
| `domain_entities.*`（美宜佳→连锁品牌名称 contains） | 维度属性过滤（`dim_chain.chain_brand_name LIKE '%美宜佳%'`） |
| `时间谓词` close_after/open_after | DWS 上 `fact_platform_store_snapshot.营业时间` 文本解析为可比较时刻 |
| `relationships.*` | 事实/维度/关系桥的 Join 键、基数和 as-of 规则 |
| `dynamic_labels.*`（高潜餐饮/夜间营业/资料完整/优先派单…） | 不要求对应物理列；查询时编译为确定性表达式和依赖图 |
| `physical_bindings.*` | 按租户/引擎绑定物理表、列、数据类型和支持能力 |
| `policies.*` | 查询编译阶段注入行列权限和租户过滤 |

语义控制面位于 Gold/DWS 与消费应用之间，但不等于 ADS。ADS、缓存和物化视图都是可选加速产物，允许删除后按版本重建。

### 13.7 动态标签执行、缓存与物化

动态标签结果键：

```text
tenant_id + entity_id + label_id + label_version +
data_snapshot_id + semantic_version + policy_version +
physical_binding_version + dependency_fingerprint
```

`computed_at / engine_version / sort_rule / prediction_model_version / expires_at` 是缓存元数据，不进入等价命中主键；否则每次计算都会产生新键而无法复用。`dependency_fingerprint` 覆盖所有依赖源、预测模型和关系版本。

对进入业务决策、导出或写回的结果持久保存 `evidence`（命中的原子事实、指标阈值、适用条件和来源版本），以回答“为什么该售点入选”；纯预览型 Virtual 结果可随会话失效，但若被用户确认或复用，必须转入可审计结果账本。

| 模式 | 适用条件 | 失效条件 |
|---|---|---|
| Virtual 即时计算 | 新标签、低频、个性化、规则经常变化 | 查询结束或会话结束 |
| Versioned Cache | 同一租户、数据快照和规则版本重复查询 | 任一版本/权限/数据新鲜度变化 |
| Materialized 选择性物化 | 高频、稳定、计算昂贵、跨用户复用、有明确 SLA | 规则升级、数据刷新、权限变化或人工撤销 |

物化决策输入包括：查询频率、单次成本、可复用实体比例、规则稳定性、刷新成本、存储成本和新鲜度 SLA。物化结果不是业务真相，唯一真相仍是“原子事实 + 规则版本 + 数据快照”。

刷新与一致性要求：

- 同一发布批次使用一致的数据/语义/权限快照，禁止半刷新结果；
- 支持增量刷新失败后保留上一可用版本，并显式标记陈旧时间；
- 迟到数据只使受影响分区/实体失效，不能默认全库重算；
- 并发刷新使用单写者或原子版本切换，消费者只读取已提交版本；
- 规则升级先生成新版本，验证通过后切换别名；旧版本保留到回滚窗口结束。

### 13.8 Warehouse Adapter 与能力矩阵

统一逻辑计划包含：投影、过滤、关系、粒度、聚合、窗口、时间谓词、动态标签依赖、权限和输出规范。Adapter 必须声明：

- 支持的算子、Join、窗口和 as-of 能力；
- 分区/聚簇/索引/物化能力；
- 参数化查询和权限下推方式；
- 快照/时间旅行和结果复现能力；
- 不支持能力的确定性回退或拒绝，不得静默改变语义。

PRD 不预先锁定 Snowflake、Delta、Iceberg 或任何 BI 厂商。轻量模式继续以 pandas 为默认；DataFusion/DuckDB 作为本地列式引擎；企业模式按客户现有平台选择 Adapter 并基准测试。

### 13.9 数据契约、质量和血缘

每个数据产品声明：粒度、主键、字段类型、可空性、新鲜度、Schema 兼容策略、负责人和数据分类。查询链路记录：

```text
自然语言 → 候选语义 → 澄清/选择 → DSL → 动态标签 →
逻辑字段/关系 → 物理表列 → 数据快照 → 结果与行动
```

规划对接 OpenLineage 的 Dataset/Job/Run 事件或等价标准；字段级和规则级血缘必须能够定位某个结论使用了哪些物理字段、规则版本和执行批次。

### 13.10 落地路径（不碰原始数据）

> 原始 parquet 仅作只读源，**任何建模脚本均生成到独立输出目录，绝不修改/删除原始文件**。

| 阶段 | 动作 | 风险 | 状态 |
|---|---|---|---|
| Stage 0 | 轻量模式：列裁剪、数据/语义版本、动态标签证据、查询负载采集；原始文件只读 | 低 | 🔲 规划 |
| Stage 1 | 建立 `entity_store`、来源映射、关系桥、历史属性和严格粒度事实；将三列潜力演进为场景/模型事实 | 中 | 🔲 规划 |
| Stage 1 | 语义包与逻辑计划：实体、指标、关系、规则、权限、物理绑定；实现首个 Warehouse Adapter | 中 | 🔲 规划 |
| Stage 2 | 自适应缓存/物化、血缘标准、BI 上下文协议；按选定引擎评估分区、聚簇、时间旅行和增量刷新 | 中 | 🔲 规划 |

## 14. HIP 语义澄清与安全学习

### 14.1 产品目标

开放世界中永远会出现系统未登记、含糊、缺参或跨部门口径冲突的表达。HIP 不承诺“理解所有语义”，而是让系统：

1. 知道自己何时不确定；
2. 定位不确定的是实体、指标、时间、范围、比较对象还是标签规则；
3. 选择成本最低且信息增益最高的澄清动作；
4. 将经验证的纠正沉淀为候选知识；
5. 在治理后升级语义系统，而非在生产中直接试错。

### 14.2 状态、动作与奖励

| 要素 | 内容 |
|---|---|
| 状态 | 原始问题、Top-K DSL、候选差距/熵、实体/指标覆盖、适用业态、会话与BI上下文、历史纠正、风险等级 |
| 动作 | 直接执行；询问缺失概念；展示两个口径；确认当前理解；拒答；转业务分析人员 |
| 正奖励 | 用户确认正确；执行结果通过验证；纠正被后续查询可靠复用 |
| 负奖励 | 静默错误（最高惩罚）；无效/重复提问；用户放弃；非法 DSL；延迟和交互成本 |

强化学习优化的是澄清策略，不是业务真相。指标阈值、动态标签、权限和实体映射仍由语义控制面确定。

### 14.3 技术路线

| 阶段 | 方法 | 上线方式 |
|---|---|---|
| Stage 0 | 规则 + 校准置信度 + 风险阈值 | 先实现弃权、单选澄清和完整日志 |
| Stage 1 | Contextual Bandit / Learning-to-Rank | 从审核后的历史日志离线训练；Shadow与A/B验证 |
| Stage 2 | 层级强化学习 | 仅在多轮澄清占比和样本量足够时评估 |

多数查询只有“执行还是问、问哪个”的一步或少步决策，优先采用 Contextual Bandit，比完整在线 RL 更安全、数据效率更高。

### 14.4 反馈治理

```text
用户纠正
→ 纠正证据日志
→ 去重/聚类/质量标注
→ 离线反事实评估
→ 业务负责人审核
→ 租户灰度发布
→ 监控与可回滚版本
```

禁止项：

- 不用未验证的隐式点击直接改全局口径；
- 不跨租户复用私有业务纠正；
- 不让策略为了“少提问”而降低安全阈值；
- 不允许策略绕过 `validate_query`、权限和数据契约；
- 不把用户选择候选解释等同于客观业务真相，必要时要求口径负责人确认。

## 15. 产品护城河与客户表达

护城河不是某个模型或“能聊天”，而是随客户使用持续积累的企业决策资产：

1. **实体资产**：跨来源售点、品牌、平台门店的身份解析和人工审核历史；
2. **语义资产**：指标、维度、适用条件、业务黑话、动态标签和版本；
3. **执行资产**：确定性 DSL、关系计划、权限、物理绑定、证据和回归样本；
4. **学习资产**：真实歧义、澄清策略、经验证纠正和失败模式；
5. **行动资产**：哪些标签、名单和建议真正被采纳并产生业务效果。

目标客户表达（相关能力发布后）：

> 不需要为每一个新问题重做报表或等待标签加工。系统基于受治理的企业事实即时组合标签；不确定时主动澄清；答案可解释、可复现，并能直接进入 BI、名单和业务行动。
